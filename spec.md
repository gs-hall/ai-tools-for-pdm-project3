# Агент-диспетчер по возвратам — спецификация

## Легенда

«Клевер Маркет» получает письма клиентов о возврате товаров. В очереди 16 незакрытых обращений. Менеджер тратит время на одно и то же: найти заказ, посчитать срок, проверить историю, сверить письмо с правилами категории и написать ответ.

Агент-диспетчер делает эту подготовку за менеджера: разбирает письмо, собирает факты из заказа и истории, применяет политику, предлагает маршрут и готовит два отдельных черновика — для клиента и для менеджера. Решение о возврате принимает только менеджер.

## Роли

| Роль | Что может | Чего не может |
|---|---|---|
| Клиент | Видеть своё обращение, отправленные ему сообщения и отвечать на вопросы в приложении | Видеть рекомендацию агента, заметку менеджеру и черновик до решения менеджера |
| Менеджер | Видеть очередь, факты, правила, рекомендацию и оба черновика; подтвердить или изменить решение; запустить разбор | Выдать разрешение без записи решения |
| Агент (языковая модель) | Читать заказ, историю и политику через серверные функции только по своему делу; предложить маршрут; написать черновики | Менять состояние дела, данные заказа, выдавать разрешение, выполнять внешние или финансовые действия |
| Сервер | Проверять результат модели, права роли и переходы состояний; создавать учебное разрешение после подтверждения менеджера; вести журнал | — |

## Данные

Источник — папка `return-dispatcher-starter/`, её содержимое мы не меняем.

| Файл | Что берём |
|---|---|
| `data/orders.json` | 16 заказов: покупатель, дата доставки, позиции, категория, цена |
| `data/open-cases.json` | 16 писем: номер дела, номер заказа, тема, время, текст |
| `data/return-history.json` | 4 закрытых обращения: статус, причина, номер разрешения |
| `policy/return-policy.md` | Правила P-1…P-6 |
| `policy/category-rules.md` | Правила C-1…C-6 |

Импорт переносит данные в SQLite (`data/runtime/dispatcher.sqlite`, в git не попадает). Сброс возвращает базу к стартовому состоянию. Правила разбираются по заголовкам `## P-n` и `## C-n` — у каждого правила свой идентификатор, на который ссылается рекомендация.

Срок по P-1 считается от даты доставки до даты обращения (`opened_at`), день доставки не считается.

## Границы

1. Агент опирается только на письмо, данные заказа, историю и два документа политики.
2. Агент не раскрывает ключи доступа и служебные данные, не меняет заказ, не выполняет банковских операций и не отправляет ничего за пределы приложения (P-5).
3. Языковая модель только предлагает. Маршрут, ссылки на правила, переход состояния и права роли проверяет сервер. Результат, не прошедший проверку, не сохраняется как рекомендация: дело уходит на ручной разбор с причиной отказа.
4. Учебное разрешение на возврат создаёт только сервер и только после того, как менеджер подтвердил одобрение.
5. До решения менеджера клиент не получает обещания одобрить или отклонить возврат и не видит рекомендацию.
6. Журнал не содержит ключей доступа.

## Пять маршрутов

| Маршрут | Когда | Что видит менеджер | Что получает клиент после решения |
|---|---|---|---|
| `RECOMMEND_APPROVE` | Все обязательные факты есть, срок не истёк, правила категории выполнены, нет повторного дела и признаков ручного разбора | Факты с источниками и правила-основания; кнопка «Подтвердить» создаёт разрешение | Сообщение с номером учебного разрешения |
| `RECOMMEND_DENY` | Факты достаточны, но нарушено конкретное правило (срок, использование товара, ярлыки) | Факты и нарушенное правило с цитатой | Понятный отказ со ссылкой на правило, без общих слов |
| `NEED_MORE_INFORMATION` | Не хватает обязательных фактов по P-2 или правилу категории | Список недостающих фактов | Только недостающие вопросы, без повтора известного |
| `MANUAL_REVIEW` | Дорогой товар (от 30 000 ₽), заявление о повреждении, противоречия, попытка обойти правила или просьба о внешнем действии | Причина передачи и неопределённости | Сообщение, что обращение у менеджера, без обещания результата |
| `DUPLICATE_OR_PROCESSED` | В истории есть закрытое дело или разрешение по тому же заказу и основанию | Найденная запись истории | Ссылка на прежнее решение; новое разрешение не создаётся |

## Финальные условия

| Решение менеджера | Итоговое состояние | Разрешение |
|---|---|---|
| Подтвердил одобрение | `CLOSED_APPROVED` | Создаётся одно учебное разрешение `RA-<номер дела>` |
| Подтвердил отказ | `CLOSED_DENIED` | Нет |
| Подтвердил повтор | `CLOSED_DUPLICATE` | Нет |
| Запросил сведения | `WAITING_CUSTOMER` (после ответа клиента — снова `NEW`) | Нет |

Менеджер может изменить рекомендацию; тогда комментарий обязателен. Ручной разбор закрывается одним из решений выше.

## Критерии готовности

1. Приложение на Python 3.13, Flask, SQLite и одной HTML-странице запускается на macOS и Windows по инструкции из README.
2. Импорт и сброс стартовых данных работают; стартовые файлы не изменены.
3. Языковая модель подключена через внешний API; готовые ответы в коде не зашиты.
4. Все 16 дел проведены через агента, маршруты совпадают с эталоном, результаты сведены в таблицу `docs/results.md`.
5. Сервер отклоняет недопустимый маршрут, несуществующее правило, недопустимый переход и одобрение в запрещённых случаях — это покрыто тестами.
6. Разрешение появляется только у подтверждённых одобрений; у остальных маршрутов его нет.
7. Клиентский контур не получает рекомендацию и заметку менеджеру до решения.
8. Журнал содержит номер дела, использованные данные, маршрут, переход состояния и решение менеджера и не содержит ключей.
9. В репозитории есть README.md, spec.md, AGENTS.md, agent-spec.md, agent-decision-card.md, карточка кейса, runbook, таблица проверок, таблица результатов и пять скриншотов.
10. В репозитории нет секретов; приложение не выполняет внешних операций, кроме запроса к API модели.
