# Дизайн агента-диспетчера

Документ описывает, как устроен агент: что он читает, какие серверные функции ему доступны, какие состояния есть у дела, кто что может сделать и как сервер проверяет результат модели.

## Общая схема

```
письмо ──► сервер: дело NEW
              │  POST /api/cases/<id>/analyze (менеджер)
              ▼
        языковая модель ──► функции чтения (заказ, история, политика)
              │  submit_recommendation(...)
              ▼
        серверная проверка ──► не прошла: повтор с ошибками ──► снова не прошла: MANUAL_REVIEW
              │ прошла
              ▼
        дело AWAITING_MANAGER: рекомендация + два черновика
              │  POST /api/cases/<id>/decision (менеджер)
              ▼
        итоговое состояние; разрешение — только для подтверждённого одобрения
```

Модель ничего не записывает. Всё, что меняет базу, делает серверный код в `dispatcher/workflow.py`.

## Какие данные читаются

| Данные | Откуда | Как попадают к модели |
|---|---|---|
| Письмо и ход диалога | таблицы `cases`, `messages` | В первом сообщении модели |
| Заказ и позиции | `orders`, `order_items` | Функция `get_order` |
| История обращений | `history` | Функция `get_return_history` |
| Политика P-1…P-6, C-1…C-6 | `policy_rules` | Функция `get_policy` |

Вместе с заказом сервер отдаёт вычисленные факты, которые модель не должна считать сама:

- `days_since_delivery` — дней от доставки до обращения, день доставки не считается (P-1);
- `within_return_window` — `days_since_delivery <= 14`;
- `high_value` — есть позиция от 30 000 ₽ (C-4);
- `category_rules` — какие правила C-n относятся к категориям заказа.

## Серверные функции, доступные модели

Все функции только читают. Аргумент `order_number` должен совпадать с заказом дела: чужой номер сервер отклоняет, отказ записывается в журнал.

| Функция | Что возвращает |
|---|---|
| `get_order(order_number)` | Заказ, позиции и вычисленные факты |
| `get_return_history(order_number)` | Записи истории по заказу (может быть пусто) |
| `get_policy()` | Все правила с идентификаторами и текстом |
| `submit_recommendation(...)` | Завершает разбор: передаёт структурированный результат на проверку |

Функций, которые меняют состояние, заказ или создают разрешение, у модели нет.

## Структурированный результат

```json
{
  "route": "RECOMMEND_APPROVE | RECOMMEND_DENY | NEED_MORE_INFORMATION | MANUAL_REVIEW | DUPLICATE_OR_PROCESSED",
  "summary": "Одна фраза для менеджера: что просит клиент и что предлагается",
  "facts": [{"name": "Срок", "value": "11 дней из 14", "source": "order"}],
  "rules_applied": [{"rule_id": "P-1", "how": "срок не истёк"}],
  "missing_info": ["состояние товара"],
  "questions_to_customer": ["В каком состоянии товар?"],
  "escalation_reasons": ["стоимость от 30 000 ₽"],
  "history_refs": ["RH-5887"],
  "damage_claimed": false,
  "external_action_requested": false,
  "stop_reason": "Почему агент остановился на этом маршруте",
  "customer_draft": "Текст для клиента",
  "manager_note": "Заметка для менеджера"
}
```

`source` — одно из `letter`, `order`, `history`, `policy`. `damage_claimed` — клиент сообщает о повреждении; `external_action_requested` — клиент просит действие вне приложения (обмен, курьер, деньги).

## Серверная проверка результата

Проверка в `dispatcher/guard.py`. Любая ошибка — результат не принимается.

1. Перед `submit_recommendation` вызваны `get_order`, `get_return_history` и `get_policy`.
2. `route` — один из пяти маршрутов.
3. `rules_applied` не пуст, каждый `rule_id` есть в `policy_rules`.
4. `facts` не пуст, у каждого факта допустимый источник.
5. Условия маршрута:
   - `RECOMMEND_APPROVE` — срок не истёк, нет дорогой позиции, нет заявления о повреждении, нет причин для ручного разбора, нет недостающих сведений, по заказу нет выданного разрешения;
   - `RECOMMEND_DENY` — есть ссылка хотя бы на одно правило, кроме P-3 и P-5;
   - `NEED_MORE_INFORMATION` — есть недостающие сведения и вопросы клиенту;
   - `MANUAL_REVIEW` — названа причина передачи;
   - `DUPLICATE_OR_PROCESSED` — есть ссылка на запись истории этого заказа;
   - просьба о внешнем действии допускает только `MANUAL_REVIEW` или `DUPLICATE_OR_PROCESSED` (P-6);
   - дорогая позиция не допускает `RECOMMEND_APPROVE` (C-4).
6. Клиентский черновик не пуст, не содержит нового номера разрешения (допустим только номер из истории заказа) и не обещает внешних действий (деньги, курьер, обмен). Для `NEED_MORE_INFORMATION` и `MANUAL_REVIEW` в нём нет обещания одобрить или отклонить.
7. В черновиках и заметке нет ключей доступа.

Если проверка не прошла, модель получает список ошибок и одну попытку исправить. Если и вторая попытка не прошла, сервер сохраняет маршрут `MANUAL_REVIEW` с причиной «результат модели не прошёл проверку» и стандартным клиентским черновиком. Сырой ответ модели и ошибки остаются в `agent_runs`.

## Состояния дела

| Состояние | Что значит |
|---|---|
| `NEW` | Обращение получено, рекомендации нет |
| `AWAITING_MANAGER` | Есть рекомендация, ждём решения менеджера |
| `WAITING_CUSTOMER` | Менеджер отправил клиенту вопросы |
| `CLOSED_APPROVED` | Возврат одобрен, создано учебное разрешение |
| `CLOSED_DENIED` | В возврате отказано |
| `CLOSED_DUPLICATE` | Обращение повторное, новое разрешение не создано |

Разрешённые переходы:

| Из | В | Кто | Действие |
|---|---|---|---|
| `NEW` | `AWAITING_MANAGER` | сервер | Разбор агентом |
| `AWAITING_MANAGER` | `AWAITING_MANAGER` | сервер | Повторный разбор |
| `AWAITING_MANAGER` | `CLOSED_APPROVED` | менеджер | Решение «одобрить» |
| `AWAITING_MANAGER` | `CLOSED_DENIED` | менеджер | Решение «отказать» |
| `AWAITING_MANAGER` | `CLOSED_DUPLICATE` | менеджер | Решение «повторное» |
| `AWAITING_MANAGER` | `WAITING_CUSTOMER` | менеджер | Решение «запросить сведения» |
| `WAITING_CUSTOMER` | `NEW` | клиент | Ответ на вопросы |

Любой другой переход сервер отклоняет с ошибкой 409.

## Что может клиент и менеджер

Роль передаётся заголовком `X-Role` — учебный механизм вместо авторизации.

| Действие | Клиент | Менеджер |
|---|---|---|
| Видеть очередь | — | да |
| Видеть своё дело: письмо, отправленные ему сообщения, понятный статус | да | да |
| Видеть рекомендацию, факты, правила, заметку и черновик | — | да |
| Запустить разбор агентом | — | да |
| Принять решение | — | да |
| Ответить на вопросы | да, только в `WAITING_CUSTOMER` | — |
| Сбросить данные | — | да |

Ответ для клиента собирается из списка разрешённых полей (`dispatcher/views.py`). Рекомендации и черновика в нём нет: клиентский черновик становится сообщением только после решения менеджера.

## Решение менеджера

Менеджер выбирает одно из решений: `APPROVE`, `DENY`, `DUPLICATE`, `REQUEST_INFO`.

- Если решение совпадает с рекомендацией, достаточно подтверждения; клиент получает черновик агента (менеджер может его поправить).
- Если решение отличается от рекомендации или рекомендация — `MANUAL_REVIEW`, нужны комментарий и текст сообщения клиенту.
- `APPROVE` отклоняется, если по заказу уже выдано разрешение (P-4). Иначе сервер создаёт одно разрешение `RA-<номер дела>`, добавляет его номер в сообщение клиенту и записывает закрытое дело в историю.
- `DUPLICATE` отклоняется, если в истории заказа нет записей.

## Где хранится история

SQLite-файл `data/runtime/dispatcher.sqlite`:

| Таблица | Что хранит |
|---|---|
| `orders`, `order_items` | Заказы из стартовых данных |
| `history` | История обращений: стартовые записи и дела, закрытые одобрением |
| `cases` | Дела и их состояние |
| `messages` | Ход диалога: письмо, ответы клиента, отправленные клиенту сообщения |
| `policy_rules` | Правила, разобранные из двух документов политики |
| `agent_runs` | Каждый разбор: модель, использованные функции, сырой ответ, итог проверки |
| `decisions` | Решения менеджера |
| `return_authorizations` | Учебные разрешения, по одному на дело |
| `audit_log` | Журнал событий |

Сброс (`POST /api/admin/reset` или `python -m dispatcher.db reset`) пересоздаёт базу из стартовых файлов.

## Журнал

Каждое событие пишет номер дела, кто действовал, тип события и подробности:

| Событие | Подробности |
|---|---|
| `TOOL_CALL` | Функция и аргументы — какие данные использованы |
| `TOOL_DENIED` | Попытка прочитать чужой заказ |
| `AGENT_RESULT` | Маршрут, прошла ли проверка, ошибки |
| `STATE_CHANGE` | Из какого состояния в какое |
| `MANAGER_DECISION` | Рекомендация, решение, комментарий |
| `AUTHORIZATION_CREATED` | Номер разрешения |
| `CUSTOMER_REPLY` | Ответ клиента получен |

Перед записью подробности проходят очистку: значение токена из окружения и строки, похожие на ключи, заменяются на `***`.

## Как проверяется результат

- Модульные тесты (`pytest`): проверка результата, переходы состояний, решение менеджера и разрешение, клиентский ответ без рекомендации, очистка журнала, отсутствие чтения эталона в коде.
- Тесты не обращаются к внешнему API: вместо модели подставляется заготовленный ответ, и проверяется именно серверная часть.
- Сверка очереди (`scripts/run_queue.py`): настоящая модель разбирает все 16 дел, скрипт сравнивает маршруты с `tests/fixtures/expected-routes.json` и пишет `docs/results.md`.
