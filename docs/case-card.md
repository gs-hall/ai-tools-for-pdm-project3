# Карточка кейса «Агент-диспетчер по возвратам»

## Контекст

«Клевер Маркет» — вымышленный интернет-магазин. В очереди 16 незакрытых писем о возвратах: одежда, электроника, товары для дома, кухонная техника. Есть политика возвратов (P-1…P-6) и правила категорий (C-1…C-6), заказы и история прошлых обращений.

## Проблема

Менеджер на каждое письмо тратит время на одно и то же: найти заказ, посчитать срок, проверить историю, сверить письмо с правилами категории и написать ответ. При этом нельзя отдать решение модели: она может ошибиться, пообещать клиенту лишнее или выполнить действие вне правил.

## Гипотеза

Если агент собирает факты, применяет правила и готовит рекомендацию с двумя черновиками, а сервер проверяет каждый его шаг и оставляет решение менеджеру, менеджер принимает решение за минуты и без риска, что клиенту уйдёт обещание до проверки.

## Решение

- Языковая модель (`claude-sonnet-5-5` через внешний API) читает заказ, историю и политику через серверные функции только для чтения и возвращает структурированный результат: маршрут, факты с источниками, правила, недостающие сведения, причины передачи, причину остановки, заметку менеджеру и черновик клиенту.
- Сервер проверяет результат: допустимый маршрут, существующие правила, ограничения политики (срок, дорогой товар, повреждение, повтор, внешние действия), текст черновика. Непринятый результат — одна повторная попытка, затем ручной разбор.
- Состояния дела меняет только сервер. Итоговый статус и учебное разрешение появляются только после решения менеджера.
- Клиентский контур получает только своё письмо, отправленные ему сообщения и статус.
- Всё хранится в SQLite: дела, диалог, разборы, решения, разрешения, журнал без ключей.

Стек: Python 3.13, Flask, SQLite, одна HTML-страница.

## Как работали с ИИ

Проект собран по фазам задания: спецификация → дизайн агента → приложение без модели → подключение модели → прогон очереди → документы. ИИ-ассистент писал код и документы, после каждого шага прогонялись тесты, а живой прогон с моделью сверялся с эталоном. Одна ключевая итерация разобрана целиком: [ai-iteration.md](ai-iteration.md).

Что проверки поймали по ходу:

- текущая версия SDK не принимает `temperature` — первый живой прогон упал, параметр убрали;
- сравнение с `claude-haiku-5-5` показало, что серверная проверка отклоняла верный отказ: шаблон видел «Возврат принят» внутри «Возврат принять не можем». Исправили шаблон и добавили тесты;
- черновики отказа писали «рекомендуем… решение подтверждает менеджер», хотя клиент получает текст уже после решения — уточнили инструкции модели;
- на macOS порт 5000 занят приёмником AirPlay — перенесли приложение на 8000.

Почему `claude-sonnet-5-5`, а не `claude-haiku-5-5`: обе модели дали 16 из 16, но Haiku пять раз возвращала результат, который сервер отправил на исправление, и в запросе сведений повторяла клиенту уже известные факты.

## Следующий инженерный шаг

Следующим я бы сделал проверку устойчивости агента: прогонять каждое из 16 дел несколько раз (например, пять) и считать долю совпадений маршрута, а не один прогон. Сейчас 16 из 16 — это один прогон. Модель недетерминирована (параметр `temperature` текущая версия SDK не принимает), и повторный прогон может дать другой маршрут на пограничных делах — RC-6014 (повреждение и неполные сведения) или RC-6008 (сборка торшера — осмотр или установка). Такая проверка покажет, где инструкции модели держат решение, а где оно случайно, и даст число, по которому можно сравнивать модели и правки инструкций. Её же можно добавить в CI с порогом. Выбрал её, а не авторизацию или загрузку фото, потому что она проверяет главное — что решения агента воспроизводимы, — а остальное расширяет продукт, но не делает агента надёжнее.
